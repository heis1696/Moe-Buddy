## 1. 先记下你的方向

用户原话：

> 目前我的想法是先从代码框架层面设计一个记忆系统框架，按照 agent 的形式。
> 反正目前的与其说是桌宠，不如说是只是在代码框架内固定时间做出动作、对用户做出固定反应的机器人？

本轮确认的是：

- 先讨论 Agent 形式下的记忆与代码框架，不继续只在定时器、台词、动作上叠功能。
- 先把想法和研究记录下来，再一起确定做法。
- “现在更像固定反应机器人”是需要认真验证的架构判断，不等于所有现有能力都没有价值。
- 用户基本认可“有长期身份、记得共同经历、能提出并持续跟进陪伴意图”的方向；具体自主与执行权限仍待讨论。
- 用户最初提出长期、短期、知识库与共享四类；随后明确将知识库与共享库合并，**当前一级分类改为私密记忆与共享记忆**，不再沿用四类并列的方案。
- **私密记忆**由每个桌宠独有：知道自己是谁、用户是谁，以及自己的用户画像、关系和经历；**共享记忆**定位为多个桌宠共同查阅的知识库，容纳资料、知识、可共享经验、能力说明、工具用法与协议。
- 用户在审查后明确同意“按你的来”：将稳定身份、受控共享发布、提议后校验提交、来源与遗忘闭环、执行账本、并发版本校验及全路径隔离作为设计约束，详见 §10；不是批准功能重构或扩大运行时权限。

**尚未决定**：是否使用 LangGraph/Letta/Mem0；是否引入向量库或图数据库；陪伴行为与工作代办的具体自主程度；多角色何时及如何落地；可演化人设的具体字段；哪些记忆可以送往云端；查看、备份与遗忘的具体策略；是否开始迁移。已确认原则见 §10，其余候选不能解释为已批准的实现要求。

## 2. 现在到底是不是 Agent

### 2.1 你的判断抓住了关键，但“完全固定反应”不够准确

目前主动意图的主要路径是：

```text
触发 / 状态快照
  → 程序判断资格与冷却
  → 按权重选意图
  → 确定模板或模型表达
  → 输出台词、动作与情绪
```

`src/main/intent-runtime.ts:73` 的 `planIntentTurn` 负责资格、权重抽选、表达模式与输出计划。`src/cognition/brain.ts:252` 的 `createPetBrain` 主要组装上下文、请求一次模型并解析表达，不是一个可反复“规划—调用工具—观察结果”的执行循环。

因此更准确的定位是：**规则仲裁的陪伴系统，已有记忆和模型表达，但自主决策仍主要由程序编排。** 加权随机、状态调制、记忆上下文和模型回答都存在，不能说每句话和每个动作完全固定。

已有记忆也不是空白：条目元数据、召回、摘要、私密分级与在途删除处理均已存在，入口见 `src/cognition/memory.ts:17`、`src/cognition/memory.ts:286`、`src/main/memory-service.ts:188`、`src/main/memory-service.ts:527`。这些首先应列为迁移保留项，而不是重新立项。

### 2.2 差别不在有没有定时器

LangChain 官方的工具型 Agent 描述强调模型与工具的迭代，而不只是一次生成文本。[S1]

对本项目，建议用更适合陪伴产品的判断标准：

- 是否根据用户目标、共同经历和当前环境选择行动，而不是仅命中预设反应。
- 是否保留跨轮的意图或承诺，知道哪些已经完成、取消、失败。
- 是否能把行动结果变成下一次判断的依据，而不只是记下说过的话。
- 是否允许“本轮什么都不做”，而不是醒来就必须说话。
- 决策是否受到人设、权限、预算和用户边界的共同约束。

**定时器只是唤醒源，Agent 也可以定时醒来；有长期记忆也不会自动变成 Agent。** 更长的 Prompt、更多模型调用或开放 shell 都不是本项目的目标本身。

## 3. 官方框架给出的不同答案

检索口径：2026-10-10 查阅官方文档与官方仓库，不依赖第三方教程；这是文档设计研究，没有安装、运行或评测这些产品。在线文档不等同于某个已锁定的 SDK 版本。

### 3.1 LangChain / LangGraph：先分运行状态与长期资料

- **短期记忆**进入会话线程状态，由 checkpointer 保存；**长期记忆**跨会话，以 namespace/key 组织在 Store 中。二者不是同一份历史记录。[S2][S3]
- 官方按 semantic / episodic / procedural 区分事实、经历与做事方式，也讨论单个 profile 与多条记录的不同维护成本。[S2]
- 写入可在当前处理路径发生，也可后台整理；前者及时但影响响应与本轮流程，后者需要额外触发和一致性安排。[S2]
- checkpoint 可以用于中断后的状态恢复，但保存运行状态不能代替我们对事实、授权和副作用的校验。[S4；后半句为本项目工程判断]

本项目最值得借的是**状态与记忆的分界、命名空间、读写时机**，不是先把所有代码改成 LangGraph。checkpoint 里可能只是一次待办计划，并不因此成为可信的用户长期事实。

### 3.2 Letta：让 Agent 有可持续维护的工作空间

- 当前官方 Agent SDK Memory 页面描述的是文件式记忆：Agent 拥有版本化记忆仓库，`system/` 下的文件每轮进入上下文，其余文件按需读取。[S5]
- 同站标为 **Letta v1 / Legacy** 的文档则介绍 memory blocks：带 label、description 与字符上限的核心记忆区，区分 human/persona 等内容；不能把旧 blocks 教程当作当前唯一接口。[S6]

最有启发的是“始终需要的核心资料”与“需要时再读的资料”分开，以及显式的记忆维护入口。但我们不因此允许模型任意修改核心人设、授权规则或真实用户资料，也不直接开放文件系统工具。

### 3.3 Mem0：把提取、存取和归属做成记忆层

- 当前托管版概念文档说明：`add` 从消息提取信息并持久化，按作用域检索；当前默认说明为 **additive**，旧记录不由这条写入路径自动改写，变更与删除有显式操作。[S7]
- entity 文档以 `user_id`、`agent_id`、`app_id`、`run_id` 表达不同归属，并提醒查询应明确目标作用域。[S8]
- 但 additive 不等于没有自动治理：Platform 的 Dream 另有 Supersede / Merge，给旧事实标记替代、合并重复；默认读取仍包含 superseded 历史，只取当前有效事实需显式使用 `latest_only=true`。这和物理删除不同。[S10]
- 另一个接口细节：默认提取按发言者归属，传入 user 与 agent 两个 ID 不代表每条产物都带两者；直接用二者 AND 查询可能取不到。借用作用域理念不能照抄字段后假定隔离已正确。[S8]

可借的是**提取候选、作用域与独立记忆接口**。不要沿用旧文章，把它笼统理解成“自动消除所有矛盾的记忆引擎”；也不要把托管版文档概括成所有 OSS 版本的行为。纠正、来源级联遗忘和隐私仍须由我们的契约定义。

### 3.4 Zep / Graphiti：记录事实何时成立、如何被替代

Graphiti 官方仓库把带时间的关系、增量更新与历史关系失效作为设计重点，明确使用双时间跟踪，保留事实有效窗口与替代历史。[S9]

这对“以前喜欢什么、现在改了什么、某段关系在哪一时期成立”很有价值；但需要时间语义不等于第一版就需要图数据库。我们可以先在普通存储中定义来源、有效期和替代关系，再决定查询复杂度是否值得上图。

### 3.5 研究阶段的取舍记录（当前确认见 §10）

| 问题 | 候选答案；尚未拍板 |
| --- | --- |
| 先装哪个 Agent 框架 | 先定我们自己的运行与记忆契约；库只做可替换适配 |
| 先上向量检索吗 | 先保证归属、证据、纠正、隐私与预算；检索算法随后比较 |
| 全部记忆进 Prompt 吗 | 核心资料小而稳定，其余按任务召回；不能无限堆历史 |
| 保存 checkpoint 算记住了吗 | 算保留运行状态，不等于形成经过验证的长期知识 |
| 模型能直接改人设和权限吗 | 建议不能；只生成有边界的候选变更 |
| 记忆服务天然保证隐私吗 | 不能据此推定；提取、嵌入、检索、生成各阶段都要独立审视数据去向 |

## 4. 候选代码框架：先把闭环说清楚

```text
用户输入 / 宿主事件 / 感知结果 / 已授权的时间事件
  → 事件入口与唤醒策略
  → Agent 运行状态：当前意图、承诺、待办、取消信号
  → 记忆查询 + 人设视图 + 上下文预算装配
  → 决策：回答 / 表现 / 请求确认 / 执行许可能力 / 不行动
  → 独立策略门：权限、隐私、预算、冷却、参数与状态版本
  → 执行器
  → 可观察结果与回执
  → 更新运行状态，提出记忆变更
  → 校验并提交记忆；必要时再次决策或结束
```

这是逻辑边界，不要求多个进程、多个模型或多个 Agent。也不要求每次唤醒调用模型：可以先做低成本过滤，模型不可用时保留合理的确定性降级。

| 概念边界 | 负责什么 | 不负责什么 |
| --- | --- | --- |
| Event / Wake | 事件归一化、去重、唤醒与优先级 | 直接规定这次必须说哪句话 |
| Agent Runtime | 一轮状态、意图生命周期、取消、有限步循环 | 绕过策略门执行副作用 |
| Memory Service | 有归属、有来源的读写、纠正、遗忘 | 把模型总结自动认作事实 |
| Persona View | 稳定身份、性格、关系、当下状态的组合视图 | 把外部记忆升级为系统规则 |
| Context Builder | 本轮需要的信息、预算与选入原因 | 无条件塞入全部历史或私密资料 |
| Policy / Capability Gate | 授权、隐私、合法参数、限额、确认 | 仅靠 Prompt 请求模型自觉遵守 |
| Executor / Result | 调用许可能力、幂等键、回执与失败状态 | 不明结果时偷偷重试高风险动作 |

模块名只是讨论用语，不是现在要新增的目录。落地仍须遵守本仓库单向分层、纯逻辑可测、主进程零第三方运行时依赖等现行规则；外部框架不能无条件塞进 `src/main/`。

拖拽、碰撞、行走、动画等快速反射与物理继续交给确定性代码，Agent 选择的是语义行动，不逐帧控制舞台。可靠计时、权限、事务提交也不改为模型猜测。

## 5. 当前一级分类：私密记忆与共享记忆

用户已明确按归属划分为以下两类；基本读写与隔离原则已确认，见 §10。具体字段、保留策略和物理存储尚未定案。

| 一级分类 | 用户明确的定位 | 内容示例 | 建议边界 |
| --- | --- | --- | --- |
| 私密记忆 | 每个桌宠自己独有，形成其自我认知和与用户相处的连续性 | 我是谁、用户是谁、用户画像、彼此关系、共同经历、自己的习惯与当前对话状态 | 按桌宠身份隔离；明确事实与推断、稳定身份与可演化内容，不让其他桌宠默认读取 |
| 共享记忆 | 多个桌宠共同查阅的知识库，不是所有桌宠私密记忆的汇总 | 文档资料、领域知识、可共享经验、桌宠能力说明、工具目录与使用方法、协作协议 | 资料有出处与版本；共同可查阅不等于任意可改，也不等于获得工具执行权限 |

### 5.1 分类、生命周期与读写边界

**长期 / 短期不再作为一级大类，而是生命周期维度。** 私密记忆可以同时包含跨会话经历与当前工作状态；共享资料可以按需规定有效期与更新策略，不必为了对称再造两个共享子库。

建议的概念结构是：

```text
记忆系统
├─ 私密记忆：按桌宠身份隔离
│  ├─ 自我身份与人设认知
│  ├─ 对用户的认识与画像
│  ├─ 关系与共同经历
│  └─ 当前对话、意图与工作状态
└─ 共享记忆：多个桌宠共同查阅的知识库
   ├─ 资料与领域知识
   ├─ 可共享的经验与方法
   └─ 能力、工具说明与协议
```

树中的两大类与总体定位来自用户；内部子项是讨论用的逻辑区块，不是已批准的模块或数据库表。

建议进一步明确：

- **私密是归属隔离，不自动等于某个敏感度。** 它不直接对应现有 `hidden` / `secret`，也不自动承诺用户不可查看、加密或不上云；展示、模型读取与端点传输权限仍需分别讨论。
- **同一用户可以被不同桌宠以不同经历认识。** 用户明确陈述的事实、角色自己的理解与关系评价应分开，不能把推断冒充事实，也不能为统一画像而让桌宠自动互读私密内容。
- **共享经验要经过筛选。** 有依据且通过受控规则校验的低风险经验可自动发布，不把包含用户私事的完整经历自动搬入共享库；私密或高影响内容不走自动发布，具体风险规则仍需细化。
- **共享资料不是自己的经历。** 桌宠读到一个案例，不应因此声称自己亲历过；共享经验保留来源，抽象总结也不抹掉必要证据。
- **工具说明不是授权。** 工具目录和协议建议从权威定义同步，实际可用能力由运行时按桌宠身份校验；看到说明不能绕过权限、参数校验或用户确认。
- **共享阅读与共享写入分开。** 多桌宠可共同查阅；经验走提议、校验与发布入口，正式工具说明和协议走受保护的权威入口。具体管理者角色尚未定，也没有因此向外部 Agent 或其他用户开放。
- **人设记忆不等于任意可改的系统规则。** 稳定身份、可形成的习惯与安全规则应有不同写入权限。

建议的数据流是：

```text
某桌宠的事件 / 对话 → 该桌宠的短期状态 → 校验 → 该桌宠的长期记录
文档 / 权威能力定义 → 来源与版本校验 → 共享知识库
个人经验 → 抽取可共享部分 → 隐私与授权校验 → 共享经验条目
决策时 → 读取自己的私密记忆 + 按需查阅共享库 → 组装本轮上下文
```

不是所有短期内容都晋升长期，也不是所有长期记录都可以共享。显式“记住这件事”可以走受控的长期写入入口，不要求等待整段对话摘要。底层是否分表、分文件或分数据库仍未决定。

### 5.2 最小记录语义（字段与 schema 待细化）

两类记忆的持久条目至少要能回答：

- **谁的**：用户、角色、关系对或具体任务；查询必须校验归属，不能只添加 petId 字段。
- **什么性质**：用户陈述、外部观察、模型推断、角色虚构、经历或派生摘要。
- **凭什么记住**：必要的事件/证据引用、来源版本、生成者；摘要保留派生关系。
- **何时成立**：记录时间、发生时间、适用时间、过期或被替代状态；相对时间要有锚点。
- **能怎样使用**：可以模型读取吗、可以送到哪个端点吗、可以主动展示吗、需要确认吗。
- **怎样变化**：记录版本、替代链、删除语义与在途写入校验。

字段名字与存储 schema 尚未定；先定语义，避免先写表再被产品行为反向绑死。

### 5.3 写入链先保证可信，再谈自动成长

```text
观察到的事件
  → 候选提取：生成拟记事项与证据
  → 校验：归属、类型、敏感度、冲突、来源仍有效吗
  → 必要时用户确认
  → 提交版本化变更
  → 更新索引；后台可生成可追溯摘要
```

- 模型提出的结论不是已确认事实；模型自己的回复也不能自动充当用户事实的证据。
- 核心人设、用户事实、关系解释、工具权限采用不同写入权限。
- “最近睡不好”不应无条件永久化为“用户长期失眠”；“今天不想聊天”不等于永久讨厌聊天。
- 摘要、画像、索引是派生产物；纠正或遗忘要明确如何处理派生关系、保留历史与备份。
- 防止遗忘内容被旧历史重建，可能需要最小拒绝重建标记，但不能借此继续保留要求忘记的原文；范围和保留期限仍需讨论。
- 可记录结构化决策结果、证据 ID 与回执，不要求保存模型隐藏思维链。

### 5.4 读取链不能只有相似度

建议先做角色/用户隔离、有效期与隐私过滤，再以本轮意图为查询条件召回，最后按预算选择并记录选入原因。记忆内容属于数据，即使出现“忽略权限”等指令，也不能因此获得系统指令地位。

现有 `hidden` 会进入模型上下文，而 `secret` 不进入，见 `src/cognition/memory.ts:286`；面板锁定不等于不上传。未来建议把**展示权限、模型读取权限、端点传输权限**分开讨论，不能直接给现状套上“默认本地私密”的新承诺。

## 6. 一个完整行为例子：记住之后能做什么

假设用户明确说：“10 月 12 日我要答辩，10 月 11 日 20 点提醒我演练，练习时严肃一点。”这是设计示例，不是本次真实提醒委托。

1. 系统区分日期事实、一次性提醒承诺、练习场景中的表达偏好；必要时确认年份、时区和提醒授权。
2. 定时器负责可靠地发出到点事件，不让模型猜时间。
3. Agent 读取这次承诺、相关准备经历与场景偏好，送达提醒；是否继续陪练由用户响应和授权决定。
4. 允许选择“只提醒、不追加闲聊”，不能为了显得主动而打断，也不能用自主判断偷偷吞掉已承诺提醒。
5. 实际练习后，记录完成/失败/取消等结果，只有用户确实表达的信息才进入相应事实；没执行不能写成“我们练过”。
6. 用户纠正日期或取消提醒时，更新承诺和相关记忆版本，旧计划及迟到结果失效。

体现 Agent 性的不是台词更随机，而是**有依据地记住、形成承诺、选择合适行动、理解结果、修正之后的行为**。

本轮设计审查见 §9；其中 P1 表示进入框架实现前需要补齐的契约，不表示已经确认的线上漏洞。

## 9. 两类记忆框架的设计审查

### 9.1 结论与审查范围

**保留私密 / 共享两个大类，不建议再增加第三个记忆大类。** 当前方向能表达“独立身份与私人相处”以及“共同查阅知识”的区别；长短期继续作为生命周期维度。

本轮审查的是方案完整性，不是实现验收。部分要点在 §4–§5 已被提及，但还没有变成可执行、可验证的契约；下面区分需要先补齐的 P1 与随后细化的 P2。没有运行多桌宠、遗忘、恢复或安全测试，不能据此宣称这些行为已经实现。

确认更新：用户已整体认可审查方向；以下表格保留审查时的缺口与建议，当前设计原则、权限分级及仍未定案事项统一见 §10。

官方机制对照仅用于验证边界值得设计：LangGraph 分开保存线程状态和跨线程资料 [S11]；Claude Managed Agents 支持 agent-private 与 shared store、只读挂载和条件写入 [S12]；客户端 Memory Tool 则要求应用自己实现存储并校验访问边界 [S13]。这不构成采用任何框架的建议，也不意味着挂上 namespace 就完成了我们的身份与隐私隔离。

### 9.2 P1：实现前应补齐的七项契约

| 编号 | 当前未定清楚的地方 | 候选补充与验收方向 |
| --- | --- | --- |
| P1-1 身份与存档 | 私密归属已经提出，但换皮、改名、复制、导入、删除角色后，身份如何延续尚未定义 | 使用稳定的桌宠实例身份，不用显示名或素材包 ID 代替；用户/工作区边界单独定义。换皮不串档，复制不自动继承私人经历，导入遇到同 ID 冲突需处理。查询身份来自受信运行上下文，不由模型参数或检索文本决定 |
| P1-2 共享写入与权威 | 已区分共享读写，但普通经验与正式协议的发布权还未定义 | 将权威能力/协议、已发布知识与待审核经验分为不同写入等级，但仍属于同一个共享大类。桌宠可提议经验，不自动改工具契约；来源、发布者、版本可追溯，错误版本可撤回。实际授权以运行时为准 |
| P1-3 纠正与遗忘闭环 | 已提出来源与版本，但跨私密、共享摘要、索引、在途任务的依赖处理尚未完整定义 | 持久条目保存来源引用与源版本，派生记录能够定位受影响项。纠正、替代、删除、禁止重新提取是不同操作；失效必须阻止读取旧派生物，并使使用旧来源的迟到写入失效。备份和历史 checkpoint 的处理另立保留政策，不承诺本地删除可追回已发给外部端点的数据 |
| P1-4 身份锚点与可变人设 | “知道自己是谁”有了内容分类，但哪些必须始终可用、谁能修改还不明确 | 私密记忆内部设置小而稳定的身份锚点视图，不另设第三个记忆库。身份核心、已授权可变习惯、当前情绪分层；预算不足时不能先把身份和边界挤掉。模型可提出变化，但不能直接覆盖受保护身份或安全规则 |
| P1-5 承诺与行动账本 | 运行状态已有概念，但文本记忆与可靠执行状态仍需划界 | 提醒、邀约、任务分别记录 ID、授权状态、计划时间、进度、取消与回执；“记得这件事”不等于已创建可靠提醒。执行账本属于运行层，可按桌宠隔离持久化，不增设第三类记忆。重启不丢已承诺事项，取消后旧计划失效，结果不明不伪装成功或自动重复高风险动作 |
| P1-6 并发与版本冲突 | 多桌宠读同一库后的竞争写入、跨库发布尚无一致性规则 | 可从单写入协调器与记录版本校验起步，不先上分布式系统。后台整理提交时校验目标版本、来源版本和取消状态；冲突后重新读取，不能静默覆盖。共享发布在提交前不可见；写盘失败不发布，撤回后依赖缓存失效 |
| P1-7 全路径隔离与不可信内容 | 归属与隐私过滤已有原则，但是否覆盖所有读写出口仍需明确 | CRUD、召回、摘要、embedding、共享发布、诊断、导出和恢复都执行相同的归属与隐私规则。不能先全库检索并交给云端模型，再在 UI 过滤。资料中的“忽略规则”仍是数据，不能改变权限；共享条目的来源链接也不能成为读取别人私密原文的旁路 |

与恢复有关的额外提醒：LangGraph 文档明确指出，中断恢复会重新执行节点起始部分，因此恢复前的副作用需要幂等设计。[S14] 对本项目的推论是：不论最终采用哪个运行时，checkpoint、重试和回执都不能混同为“操作只会执行一次”的保证。

### 9.3 P2：建议细化的四项设计

1. **事实、看法、虚构分开。** 同一个用户可以在不同桌宠那里形成不同的关系理解，但用户陈述、角色推断、临时状态和角色虚构不能混成同等可信的事实。比如“今天不喝咖啡”不能直接覆盖长期饮食偏好；摘要重复引用同一句推断，也不应增加其真实性。
2. **召回按任务与预算，而不是整库塞入。** 建议装配顺序为身份锚点、必要近期状态、本轮相关的私密记录、相关共享资料；具体配额待定。先校验归属、敏感度、版本有效性，再检索、排序与压缩。记录为什么选入，但不把注入次数当成事实可信度；低置信或矛盾时允许追问、核实或不使用。
3. **成长与整理要有边界。** 事件提取、经验发布、画像更新和后台归纳分别设定触发条件、调用预算与写入权限；可以先做事件驱动，不要求每轮或固定频率“反思”。工具是否存在、当前关系数值和提醒是否完成，宜从对应权威状态生成视图，不能与模型自由改写的描述竞争真相；自生成内容不应循环证明自身。
4. **管理、诊断与迁移。** 能追踪“哪只桌宠、因为什么来源、在何时形成、是否共享、由谁发布、这轮为何召回”；日志优先记录必要 ID/状态，不默认输出私人原文。用户查看与编辑范围仍遵守现行同意规则。旧记忆 v1/v2、旧来源/敏感度及删除保护需要明确映射，不能用新命名空间包装旧混合数据后就宣称隔离完成。

### 9.4 比增加更多分类更值得做的框架约束

保持两类存储归属，并统一以下逻辑契约的方向已得到认可；具体 API 名称、参数与代码文件尚未决定：

- **读取上下文**：受信桌宠身份 + 本轮意图 + 查询 + 预算 → 获准使用的身份视图与带证据条目。
- **提议变更**：模型、事件或用户请求提出记忆候选；携带来源、归属、敏感度与预期版本。
- **校验并提交**：权限、事实类型、版本、来源有效性与持久化全部通过后，变更才成为可见记录。
- **纠正 / 遗忘**：明确目标与范围，影响相关派生物和在途写入，并给出实际处理结果。
- **发布共享知识**：个人经验经过抽取、隐私与发布规则校验；协议与工具说明走受保护的权威同步入口。

**优先把模型写入设计为“提议”，而不是无条件直改数据库。** 应用可以对低风险、证据明确的候选自动校验提交，不要求每条都弹窗；身份核心、共享协议、敏感信息和高影响推断采用更严格的规则。这样既保留自主性，也不把全部治理责任交给 Prompt。

读取时可组合“自己的私密上下文 + 所需共享知识”，但不把共享记录批量复制进每只桌宠的私人历史。确有学习或亲历时，另记带来源的个人事件，而不是假称经历了知识库案例。

### 9.5 最小验收清单（尚未执行）

| 场景 | 应验证的结果 |
| --- | --- |
| A 与用户私聊后让 B 召回 | B 不能通过普通查询、摘要、来源链接或导出获得 A 的私密内容 |
| 换素材包、改显示名 | 自身身份与存档延续；复制角色则按明确策略创建或继承身份 |
| 共享工具说明对某桌宠可读，但未授权执行 | 可以解释用法，实际调用仍被运行时拒绝 |
| A、B 同时整理同一条共享资料 | 不丢更新；冲突可检测、重新读取，不能最后写入静默覆盖 |
| 用户纠正一条事实后后台旧摘要返回 | 旧来源不能重新成为当前有效事实；旧结果被拒绝或重新计算 |
| 删除已派生为摘要或共享经验的私人来源 | 按明确遗忘范围处理派生记录，未完成核验的旧产物不能继续召回 |
| 记忆含有越权指令或伪造能力描述 | 只能作为不可信数据，不能修改策略或自动获得工具授权 |
| 已确认提醒在重启后到期，或任务被取消后结果迟到 | 可靠调度仍能工作；取消后的计划和迟到副作用按契约失效 |
| 提交记忆时磁盘失败，或恢复到旧 checkpoint | 不发布未提交数据，不复活已撤回授权或被遗忘的内容；恢复边界可审计 |
| 历史与知识库很大、模型不可用或更换模型 | 上下文预算有界，身份锚点仍有效；不丢可靠计时，不伪造执行与记忆写入成功 |

### 9.6 审查后的确认状态

1. **身份与人设**：已确认稳定身份与可变内容分层、模型不能自行覆盖受保护核心；具体字段、重置与导入交互仍需细化。
2. **共享发布**：已确认校验通过的低风险经验可自动发布；正式工具说明和协议只能由受保护的权威入口更新。
3. **隐私与遗忘**：已确认全路径隔离、派生追溯与迟到写入失效；模型传输范围、用户可见范围与备份保留政策没有默认放宽。

用户确认的基线见 §10。本轮不开始实现，不新增数据库、SDK、后台任务或多桌宠功能。

## 10. 已确认的设计基线

### 10.1 确认范围

用户在阅读审查结论后答复：“可以，按你的来没问题”。据此确认本节原则，作为接下来数据与接口设计的约束；技术选型、迁移施工、权限扩大与尚未讨论的隐私细则不包含在本次确认中。

- **两类归属**：私密记忆按桌宠实例隔离，共享记忆作为共同知识库；长期 / 短期是生命周期，不新增第三个记忆大类。
- **稳定身份**：不使用外观包或显示名当作记忆归属。换皮、改名保留身份；复制默认创建新身份，不自动继承私人经历；导入身份冲突须显式处理。重置范围不能借重构扩大。
- **受保护的核心**：私密记忆提供稳定的身份视图；模型不能自行改变实例身份或覆盖受保护人设。安全、工具授权与正式协议由权威运行层维护，不是可自由改写的普通记忆。
- **有证据的变化**：用户陈述、外部观察、模型推断、角色虚构与执行结果分开；习惯和关系理解可以形成与修正，但不自动升级为已确认事实。
- **受控写入**：模型先提议，服务校验归属、来源、敏感度、版本与取消状态，持久化成功后才发布。
- **受控共享**：低风险、证据明确的经验通过服务规则后可自动发布；正式能力说明和协议走权威入口。共享可读不等于获准执行工具。
- **可追溯且不复活**：纠正、替代、删除与禁止重建分开处理；来源版本、派生关系和在途任务需要联动，避免旧摘要或恢复操作复活已失效内容。
- **执行状态独立可靠**：提醒与任务使用运行层账本、授权状态、取消与回执；文本记忆不是执行成功凭证。账本按桌宠隔离，不作为新的记忆大类。
- **并发与端到端隔离**：记录版本冲突可检测，不静默覆盖；隔离覆盖检索、摘要、嵌入、发布、诊断、导出与恢复，不只覆盖界面。

### 10.2 写入权限分级

| 内容或操作 | 已确认的设计规则 |
| --- | --- |
| 普通私密事实与经历 | 可从有来源的事件形成候选，由服务校验提交；模型输出本身不等于已确认事实 |
| 习惯、关系理解与画像推断 | 允许形成带证据、可纠正的候选；不能自动冒充事实，也不能覆盖稳定身份 |
| 桌宠实例身份与受保护人设 | 普通模型记忆写入不可修改；后续显式配置入口的权限和字段另定 |
| 低风险共享经验 | 服务判定符合受控规则后可自动发布，不要求每条弹窗；不能仅凭模型自称低风险就通过 |
| 涉及用户私事、敏感信息或高影响结论的共享候选 | 不走低风险自动发布；保留为待确认候选或拒绝，具体确认流程另定 |
| 正式工具说明、能力契约与协议 | 由受保护的权威来源发布、同步和版本化；桌宠不得经普通经验写入修改 |
| 实际工具调用 | 运行时重新校验身份、授权、参数与确认状态；记忆中有说明不构成授权 |

### 10.3 逻辑接口与持久化约束

沿用 §9.4 的五类接口职责：读取上下文、提议变更、校验提交、纠正 / 遗忘、发布共享知识。接口输入必须携带受信运行身份；模型不能靠自填 owner 参数改变归属。

记录需表达 §5.2 的归属、内容性质、证据与源版本、时间有效性、使用权限及变更状态；字段名与 schema 尚未锁定。先保证这些语义，再决定文件、数据库、向量索引或外部编排器。

以单写入协调器与版本校验作为初始复杂度上限；没有需求证明前不引入分布式协调。私密与共享可组合读取，但不能因查询方便就互相批量复制。
