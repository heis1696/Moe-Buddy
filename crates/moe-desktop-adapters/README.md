# moe-desktop-adapters

Host-only persistence and transport adapters shared by the Windows desktop and Tauri shells. This crate depends on the existing application, runtime, memory, storage, and HTTP crates; business rules remain in `moe-chat-app` and below.

## Storage

`storage::root()` selects `%LOCALAPPDATA%/MoeBuddy/daily`. The no-argument functions retain the original host API:

- `open_application(generation, now)` opens the authoritative `LocalMemory` journal and `RawLocalStore` history and applies saved model settings with transmission disabled. If `buddies.v1` exists, it restores the selected B profile and never reads stale `settings.json` as an override.
- `load_settings()` and `save_settings(settings)` read and write only endpoint, model, and persona.
- Hosts that need execution evidence can use `save_settings_detailed_at(root, settings)`. Its `SettingsSaveError` identifies the create, write, sync, publish, registry-lock, and B-authority refusal stages and preserves the underlying `io::Error` as its source; the existing `String` save functions remain compatibility wrappers.

Hosts that own an explicit root or run synthetic isolated fixtures use `open_application_at(root, generation, now)`, `load_settings_at(root)`, and `save_settings_at(root, settings)`. They return the same types as their default-root counterparts. Opening an application restores settings but always resets transmission consent. After B onboarding, `load_settings_at` is a read-only compatibility view of the active profile and every settings save is rejected with `SettingsSaveStage::BuddyRegistryPresent`. The legacy entry points accept only a clean first-use root: a missing registry is rejected when onboarding evidence, a create candidate, instance data, or pending publication exists. They preserve legacy `settings.json` only before onboarding and never create a replacement empty memory archive for an interrupted root. API keys and consent are never written. Pending or malformed settings, damaged memory, and failed history recovery return errors while preserving the files.

Legacy application opening also requires the original memory journal whenever chat history, settings, or pending memory evidence already exists. A legacy archive with chat history and a missing `memory.v1` is rejected even when no model settings were saved. Only an unused root may initialize a journal; raw-history recovery fixtures include their original journal rather than relying on empty replacement.

### Buddy profiles

The B host entry points are `load_buddy_registry_at(root)`, `create_buddy_at(root, expected_buddies_revision, label, persona)`, `switch_buddy_at(root, expected_buddies_revision, id)`, `rename_buddy_at(root, expected_buddy_id, expected_buddies_revision, expected_profile_revision, label)`, `load_buddy_profile_at(root, id)`, `commit_buddy_configuration_at(root, expected_buddy_id, expected_buddies_revision, expected_profile_revision, persona, model)`, and `open_application_for_buddy_at(root, expected_buddy_id, expected_buddies_revision, generation, now)`. Creation signs a new stable ID with the existing host RNG and selects the new profile. `BuddyModelConfiguration::new(endpoint, model, preset_id)` builds the non-secret binding. All command APIs return a body-free `BuddyRegistrySnapshot`; load the full profile through the host-only profile API when editing persona or model settings.

The first registry load preserves the known `offline-companion` identity and migrates the legacy non-secret `settings.json` fields once. On a clean first-use root it initializes the one LocalMemory journal before publishing the registry. If legacy settings/history prove that an archive existed but `memory.v1` is missing, it refuses instead of creating an empty replacement. A bounded `buddies.onboarded` marker is file-synced before first-use side effects and retained after publication; a missing registry with that marker or `chat/instances` data is rejected. Malformed evidence, pending publication, and missing files are kept for recovery. Registry state, including persona/model content and all profile versions, is one versioned `buddies.v1` commit. `.buddies.lock` serializes registry reads and writes; `buddies.pending`, malformed versions, stale revisions, missing memory, and failed publication are typed `BuddyStorageError` results. I/O stage and source errors remain inspectable. API keys, send permission, runtime handles, and chat drafts are not stored or restored. Opening a buddy restores its model preset and profile versions, with transmission denied.

New hosts should hold one `storage::BuddyStorage` for the lifetime of the desktop host:

```rust
let mut storage = storage::BuddyStorage::open(data_root, process_generation, now_ms)?;
let current = storage.registry_snapshot()?;
let created = storage.create_buddy(current.revision, "伙伴二", "第二个人设", now_ms)?;
let second_id = created.registry.active_buddy_id.expect("created buddy is selected");
let revision = storage.registry_snapshot()?.revision;
let selected = storage.switch_buddy(&second_id, revision, now_ms)?;
let app = storage.active_application_mut()?;
```

Its methods include `open(root, process_generation, now)`, `registry_snapshot()`, `active_buddy_id()`, `buddy_profile(id)`, `active_application()`/`active_application_mut()`, `application_mut(captured_buddy_id)`, `prepare_buddy(id, expected_buddies_revision, now)`, `create_buddy(expected_buddies_revision, label, persona, now)`, `switch_buddy(id, expected_buddies_revision, now)`, and `rename_buddy(id, expected_buddies_revision, expected_profile_revision, label)`. `prepare_buddy` and `switch_buddy` restore the target and make its Chat panel available before publishing the new selection. A target-open error leaves the current selection and cached apps intact.

`commit_configuration(id, expected_buddies_revision, expected_profile_revision, persona, model, now)` is the no-consent convenience path. Hosts that collected the user's explicit transmission choice call `commit_configuration_with_runtime(id, expected_buddies_revision, expected_profile_revision, model, runtime_settings, now)`. `runtime_settings.persona` is the same candidate persona persisted with the non-secret binding, and the profile/model versions are published once before that exact version is applied with the supplied consent. API keys remain in the host process. The application is not first configured with consent disabled and then separately reconfigured.

Quit protection uses `draft_revision_set()` to capture each loaded buddy's full body-free session watermark set. `preflight_quit_draft_discard(expected, active_close_discards_active)` verifies the whole set and checks every app before any discard. After any active Chat close, capture the resulting set again and pass it to `discard_all_chat_drafts(expected)`, which rechecks the complete set, preflights every app, then discards. A revision/getter failure returns `BuddyStorageError` and must keep the host open. CloseChat continues to use the active application's current-session close action. At most eight apps can be held, matching the registry limit; selection changes keep each app's session drafts, diagnostics, and runtime watermarks in that instance.

`BuddyStorage` owns one `.buddies.lock`, one `LocalMemory` handle, and one `chat/.buddy-history.lock`. Per-buddy session-directory and RawLocal locks remain private to their applications. A second independent writer of the same root is rejected. Root history accounting remains 64 logical sessions, 256 active or pending-retirement segments, and 16 MiB. The shared memory journal keeps its existing 100,000 operation and 256 MiB limits. Registry frames are read with a 256 KiB bound before parsing; current and pending frames are each bounded separately.

`commit_configuration_with_runtime` accepts the trusted `ModelSettings` and the matching non-secret model/preset binding. The adapter verifies that their endpoint, model, and persona agree, preflights that exact configuration, publishes the profile/model revisions once, and applies the supplied transmission consent to those versions. The API key is deliberately absent from this interface and remains with the host. If the registry commit is not published, the live application keeps its prior binding; if publication is confirmed but runtime application fails, the application is quarantined and the returned error retains the source chain.

`draft_revision_set` snapshots every loaded buddy's complete body-free session watermark set. `preflight_quit_draft_discard(expected, active_close_discards_active)` compares the full set and checks draft counter capacity in every app. After a confirmed active-chat close, the host captures the resulting set again and calls `discard_all_chat_drafts(expected)`. That method rechecks all buddy IDs and watermarks, preflights all apps, then consumes the matching draft revisions. Getter, revision, or preflight errors are returned; the host must not continue exit after them.

Create, switch, rename, and configuration commits return `BuddyCommitReceipt { registry, publication, candidate }` on success. The registry publication receipt reports its exact revision, file sync, and parent-directory sync. Creation also returns `candidate: Some(BuddyCandidateDurability)`, which distinguishes `FileAndDirectorySynced` from `FileSyncedDirectorySyncUnavailable`; other commands return `None`. Candidate write, file-sync, or available directory-sync failure stops before target preparation or raw-history work. Windows directory sync may be unavailable, so this receipt does not claim crash or power-loss protection for the candidate directory entry. After candidate sync, a later creation error is wrapped in `BuddyStorageError::CandidateCommit`; `candidate_durability()` recovers that receipt and `publication_state()` continues to report the nested registry state. `BuddyStorageError::Preparation` identifies failures while opening/recovering a target app and retains its nested source; hosts treat those failures as operation-unknown when preparation may already have touched raw history. `BuddyStorageError::publication_state()` reports `NotPublished`, `Published`, or `Unknown` for the registry file only. It does not classify the whole host operation: target preparation and raw-history recovery can have their own side effects and source errors, which remain available through the error chain. A post-rename directory-sync error is `Published`; a rename error is `Unknown`; earlier pending/write/sync errors are `NotPublished`. If a persisted model binding cannot be applied to the live app, the app is closed to further storage-backed work and the error remains marked `Published`. Candidate removal and cleanup-directory sync failures use `BuddyRegistryIoStage::RemoveCandidate` and `BuddyRegistryIoStage::SyncCandidateCleanupDirectory`; both are reported as `Published`, because the registry is already committed. These receipts describe successful calls and normal-process interruption recovery; they do not promise a multi-file power-loss transaction. `buddies.v1`, LocalMemory, and raw-history files are separate commits, with no cross-file atomicity or synthetic rollback.

Creation checks both `buddies.pending` and the bounded `buddies.create-candidate` marker before signing an ID. It writes and `sync_all`s that candidate before opening its app or touching RawLocal history, then attempts parent-directory sync and returns whether that was available. Preparation failures and any registry publication failure keep the candidate marker, prepared app evidence, pending registry frame, and original error chain; retry is rejected in-process and after restart. A successful registry commit inserts/selects the prepared app before removing the marker. The adapter never deletes candidate history to make a retry succeed. This supports recovery after normal process interruption; sudden power loss may lose a new directory entry where directory sync is unavailable and is not covered by a cross-file transaction guarantee.

If registry publication becomes `Unknown`, ordinary registry getters and `active_application_mut`/`application_mut` remain closed. Recovery operations include `inspect_known_buddy(id)`, `complete_external_for_buddy(id, private_ticket, outcome, now)`, full-set draft read/preflight/discard for explicit Quit, `revoke_known_buddy(id, now)`, and `hide_management_panel_during_unknown(expected_buddy_id, expected_buddies_revision, panel, now)`. The last operation only hides a non-chat panel on the already loaded active instance under the captured registry context; it cannot open panels, access chat, select or open an instance, or create business work. Hosts must capture the ticket owner and expected body-free draft watermark set before using them.

The Tauri snapshot adds a process-only `buddyCommit`, null on startup and revocation. It records the last successful action kind, captured source buddy/revision, committed destination buddy/revision, and accepted management version. It is emitted only after persistence and any required runtime binding succeed; it contains no profile text, credential, path, or ticket and is not written to disk.

The HostWorker captures the selected buddy together with the request and returns the ticket only to that cached app. Rejected or late tickets cannot complete whichever buddy happens to be selected:

```rust
let owner = storage.active_buddy_id()?.to_owned();
let request = storage.application_mut(&owner)?.take_external_request();
if let Some(request) = request {
    let (input, ticket) = request.into_parts();
    let result = transport::start(input, api_key)?.recv()?;
    storage
        .application_mut(&owner)?
        .complete_external(ticket, result.outcome, now_ms)?;
}
```

The transport worker receives only immutable `ExternalInput` and the process credential; it never owns or replaces a `ChatApplication`. The host must complete local execution and display publication and resolve storage/close guards before calling `create_buddy` or `switch_buddy`.

Private memory remains in the single authoritative `memory.v1` LocalMemory journal, scoped by the injected `PetIdentity`. `offline-companion` keeps its legacy `chat/` history; other identities use `chat/instances/<id>/`. Every history root shares the host-owned `chat/.buddy-history.lock`; root-wide accounting still limits all profiles together to 64 logical sessions, 256 active or pending-retirement segments, and 16 MiB. Directory separation therefore does not multiply the A-stage quotas. `BuddyStorage` retains each opened app under that one lock; hosts should not use the standalone buddy opener while the shared owner is alive.

Chat history is stored under `chat/` with a versioned, body-free `sessions.v1` directory, a process-wide directory lock, and independently locked `segments/segment-NNNNNNNN/` RawLocal stores. The legacy `chat/raw-local.v1` is represented in place as a managed segment using its original authorization hint; its bytes are not copied into an unmanaged backup. New and switched-to non-archived logical sessions receive a new execution segment; archived targets remain read-only and do not gain empty writable segments on restart. Each writable transition checkpoints and seals the old raw segment, creates a blank baseline, then CAS-publishes the new directory. Those file commits are separate: pending directory files, candidate markers, orphan segments, and uncertain publication results fail closed on reopen.

The directory payload is version 2 while its filename remains `sessions.v1`. It keeps `recoveredUnsettled` separate from `externalUnknown`: verified unresolved legacy raw interactions can support an explicit isolated session, without asserting that a request was sent externally. A v1 directory supplies no recovered evidence by itself; the authorized raw scan establishes and persists that evidence before retention can remove it. A v2 directory missing the evidence field is rejected.

Cold projections use `RawLocalStore::open_projection` so opening and importing share one budgeted frame read. Retirement gate format 2 stores the full stable domain and authorization revision as well as the frame receipt. Continuation validates that binding and retains the current access through each removal step; old unbound gate records fail closed. Root peak calculations use the exact variable gate size from `retirement_gate_size`, including the domain fields.

The chat root has hard limits of 64 logical sessions, 256 active or pending-retirement raw segments, and 16 MiB for all managed files. Checkpoint and rotation preflights count the current frame plus pending raw and directory candidates; a send that triggers generation rotation reserves its next user and reply frame before rotation commits. Transmission permission and other deterministic Send gates are checked before maintenance or rotation writes, then checked again at the send commit point. Root exhaustion returns `storage_capacity_exceeded` / `NotExecuted` before admitting a new send. Startup reauthorizes every managed session and commits tightened retention before publishing successful recovery, including sealed and archived segments and legacy `chat/raw-local.v1`. Before startup retention can clear raw interaction evidence, the body-free directory durably records any unresolved interaction as `unknown`; failure to publish that summary leaves the raw source untouched, and later segment creation failure cannot restore `ready`. Cold maintenance previews the actual encoded post-sweep frame and includes pending-frame, directory, and retirement-marker candidates in the root peak. Cold history reads use a temporary authorized runtime per segment, load recent messages within 64 segments, 1 MiB of actual frame reads, 512 decoded event bodies, and 1 MiB of decoded message bodies, and stop when the 128-message window is full; a zero-message request does not open raw segments. Each segment frame is read and validated once per projection; the opaque RawLocal plan is reused for import and retains its revision, time, store owner, authorization, and lock checks. The projection never enters the active Agent/SessionRuntime. Each cold maintenance pass visits at most four segments; the application report includes completed and remaining cold segments, a capacity-block reason, and raw plus directory commit receipts, including partial progress on errors through `history_commit_receipts()`. Capacity backpressure is distinct from normal page completion. Normal 30 day and recycle 7 day retention is applied to hot and cold segments. A sealed segment retires only after the existing retention service commits and verifies an empty retained projection.

Retirement records bind the exact logical session, full stable raw domain, current authorization revision, and a freshly synced receipt for the sanitized frame revision. `open_directory` only reads and validates these records. `open` must obtain current per-session history grants, revalidate each domain and authorization revision, and hold the exact RawLocal segment lock while confirming the frame and removing its payload. RawLocal's persistent sibling gate serializes lock-file removal against legitimate opens; its local tombstone prevents standard writers from reopening the segment. Durable phase receipts distinguish frame, lock, and directory removal so an unexpected missing file or phase mismatch leaves the retirement fence and files in place. Completed gate receipts remain accounted for by the 16 MiB root budget and the advanced segment sequence is never reused. Legacy retirement strings without domain and frame evidence fail closed and are not resumed automatically.

`ChatApplication::history_commit_receipts()` exposes the last confirmed raw revision and directory revision separately. Pending-file sync is recorded independently from parent-directory sync; Windows may report the parent-directory sync as unavailable, matching RawLocal's existing durability boundary.

Disk-backed memory writes preserve ordinary persistence failures as `storage_failed` / `Unknown`. A `PersistenceError::CapacityExceeded` proven to occur before journal append maps to `memory_capacity_exceeded` / `NotExecuted`; an exact `PersistenceError::Memory(MemoryError::RevisionConflict)` remains `memory_revision_conflict` / `NotExecuted`. Both retain the original `PersistenceError` through `AppError::source`; I/O and `RecoveryRequired` are never classified as definite failures.

## Transport

`transport::start(input, key)` retains the original signature and returns a one-result receiver of `Reply`. It moves only immutable `ExternalInput` and the per-process credential to its named worker thread. The adapter accepts HTTPS or numeric loopback HTTP, disables redirects, proxies, and retries, and applies the existing timeout and response byte limits. Connection loss and unusable successful responses return `ModelOutcome::Unknown`; callers must return the original `ExternalRequestTicket` through `ChatApplication::complete_external`.

The adapter tests use random temporary roots and synthetic loopback HTTP servers. They do not read the daily user archive or contact a real model service.
